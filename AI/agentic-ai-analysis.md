## 关于这门课

吴恩达在 DeepLearning.AI 上开设的这门 Agentic AI 课程，系统性地梳理了从"用 LLM 聊天"到"用 LLM 干活"的思维框架。Datawhale 社区将其翻译整理为中文教程，发布在 GitHub 上，共五个模块：

| 模块 | 主题 | 核心内容 |
|:---:|------|----------|
| 1 | Agentic 工作流简介 | 定义、自主性等级、应用案例、任务分解、评估方法、四大设计模式 |
| 2 | 反思设计模式 | 反思的三个层次、Self-refine 论文实证、图表生成案例、外部反馈 |
| 3 | 工具使用 | 工具定义与实现、手动提示工程、代码执行、MCP 协议 |
| 4 | 构建实用技巧 | 评估矩阵、错误分析、改进策略、延迟与成本优化、开发流程 |
| 5 | 高度自治智能体 | 规划模式、代码执行规划、多智能体、通信模式 |

课程的核心命题很明确：大多数真实任务不是"给模型一个 prompt，它一次返回答案"就能搞定的。一个需求往往需要拆成好几步——查资料、做分析、写代码、跑一下看对不对、不对再改——这种迭代推进的过程，才是实际干活的方式。而这正是 agentic workflow 要解决的问题。

## 一、Module 1：Agentic 工作流简介

### 1.1 什么是 Agentic AI？

**非智能体工作流（Non-agentic / Zero-shot Workflow）：**

用户通过单一提示，要求 LLM 一次性完成整个任务。课程用了一个很直观的比喻——就像让一个人写一篇文章，"中间不能使用退格键修改"，从第一个字写到最后一个字，不能回头。人类和 AI 都不擅长这种完全线性、不可逆的创作方式。尽管如此，当前主流的大语言模型在这种约束下依然能表现得不差，但上限明显。

**智能体工作流（Agentic Workflow）：**

Agentic AI 工作流是基于 LLM 的应用程序执行**多个步骤**以完成复杂任务的过程。与 zero-shot 的关键区别在于**迭代性**和**分解性**。

课程以撰写文章为例，展示了一个完整的 agentic workflow：

1. **写大纲** — LLM 先生成文章大纲
2. **判断是否需要研究** — 另一个 LLM 评估是否需要网络搜索
3. **执行研究** — 如需搜索，调用 Web Search API 获取网页内容
4. **写初稿** — 将下载的网页内容喂给 LLM 生成初稿
5. **反思与修订** — LLM 反思初稿，判断哪里需要修改或补充研究
6. **人工审核（可选）** — 在关键节点让 LLM 请求人工验证（如确认重要事实）
7. **最终修订** — 根据反馈和自我反思完成定稿

课程给出了一个正式的工程定义：**Agentic AI 工作流是"基于大语言模型（LLM）的应用程序执行多个步骤以完成任务的过程"。**

另外还提供了一个更生活化的"AI 厨房团队"类比：把任务拆成备菜、烹饪、装盘，不同模型负责不同环节——Qwen 洗蛋打蛋，DeepSeek 控制火候和炒制，KIMI 摆盘。如果效果不行，ChatGPT 来复盘哪里出了问题，打回重做。人类只负责下达指令，多个大模型逐步协作完成复杂任务。

> 这个类比本身就很说明问题。可以做一个简单的对比实验：让 GPT-4 直接生成一份完整的技术文档，表面看着还行，细看就会发现前后逻辑有些地方对不上，技术细节也经不起推敲。但如果换成"先列大纲 → 确认后逐章展开 → 每写一章回顾前文再继续"，同样的模型，输出质量会有明显改善。吴恩达给出的定义比较务实——重点不是模型本身有多强，而是怎么组织这些步骤。

### 1.2 自主性等级（Degrees of Autonomy）

课程引入 "Agentic" 这个词而不是直接用 "Agent"，有一个很重要的语言学考量：**"Agentic" 是形容词，不是名词**。这让我们可以描述一个系统"具有某种程度的智能体特性"，而不用陷入"什么才算真正的 agent"这种定义之争。课程的核心立场是：承认不同系统有不同程度的 agentic 特性，不纠结于标签。

**低自主性（Less Autonomous）：**

在低自主性系统中，所有步骤都是预先设定的，所有工具调用都是硬编码的。LLM 的主要自主性仅体现在生成的文本上。

示例流程（写一篇关于黑洞的论文）：
1. 用户指令 → 2. LLM 生成搜索关键词 → 3. 执行网页搜索 → 4. 获取网页内容 → 5. LLM 整合成文章

课程将此比喻为 **"听话但不会动脑的助手"**——你得把每一步都交代清楚：什么时候搜索、怎么组织，AI 只负责写，你负责其他所有事情。

**高自主性（More Autonomous）：**

高自主性 agent 能独立做出大量决策，动态决定执行步骤的顺序，甚至可以**创建新的可执行工具（函数）**来完成任务。

示例流程（同样写黑洞论文）：
1. 用户指令 → 2. LLM 自主决定先做网页搜索，还额外调用 "news" 和 "arXiv" 工具获取最新科研进展 → 3. 收集结果后做判断："选最好的 5 个来源"，调用 "web fetch" 和 "pdf to text" 提取内容 → 4. 写初稿，然后自我反思——发现逻辑不够严密、数据引用不清——主动改进 → 5. 交付高质量终稿

课程将此比喻为 **"聪明又有责任心的实习生"**——知道该研究什么、怎么筛选、怎么写、怎么改，全程自主完成规划、工具使用和自我改进。

课程将 Agentic AI 的精髓总结为：**"不是'能干活'，而是'会自己想怎么干、用什么工具、干完还能自己检查改错'"**——这才是真正意义上的 agent，而不是"高级打字机"。

> 课程里这个观点我觉得特别重要——**agentic 不是非黑即白的标签，而是一个连续的光谱**。自主性越高，系统就越像一个独立的团队成员，而不只是一个工具。这也意味着你需要考虑更多事情：它会不会犯错？出错了怎么办？要不要在某些关键步骤让它停下来等人确认？课程的务实态度在实际开发中很有用——你不用想着一步到位做一个"完全自主"的系统，可以从某个环节开始，先给模型多一点决策空间，跑起来再说。

### 1.3 Agentic AI 的优势

课程从三个维度总结了 Agentic AI 相比直接生成的优势：

**性能飞跃：**

在 HumanEval 基准测试上，GPT-3.5 加上 agentic workflow，可以达到甚至超过 GPT-4 直接生成的水平。这意味着通过工作流设计带来的提升，有时候比升级模型版本还要大。

**并行加速：**

Agentic 系统中的很多步骤可以同时启动多个 LLM 实例并行处理，总耗时反而比人类顺序操作更快。比如同时让三个 agent 分别研究文献、分析数据、撰写不同章节。

**模块化设计：**

不需要在所有步骤中使用同一个 LLM。简单的步骤用快模型、便宜的模型（如 Haiku），复杂的关键步骤用最强模型（如 Opus、GPT-5），各取所长。还可以自由添加新工具或替换模型，系统架构保持灵活性。

> HumanEval 的那个对比数据值得认真对待——GPT-3.5 + agentic workflow 能达到甚至超过 GPT-4 zero-shot。这意味着如果你的预算有限，不一定要升级到最贵的模型，优化工作流设计可能是性价比更高的路径。

### 1.4 Agentic AI 的应用案例

课程举了四个应用案例，覆盖了从简单到复杂的任务光谱：

**（1）发票处理：**

PDF 转文本 → LLM 解析关键字段（发票日期、金额、供应商名称、到期日）→ 工具更新数据库。这个流程体现了一个基本模式：LLM 做"理解"和"决策"，外部工具做"执行"。

**（2）回复客户邮件：**

处理"发错货"投诉的完整流程：提取邮件中的关键信息（订单号、问题描述）→ 查询订单系统确认 → 起草回复邮件 → 人工审核 → 发送。这里体现了 human-in-the-loop 的典型位置——在面向客户的最终输出环节插入人工确认。

**（3）客服 Agent：**

用户问题五花八门（查询订单、退货、投诉、咨询产品），事先无法穷举所有情况。Agent 需要动态规划 API 调用顺序，根据条件判断后续行动，必要时升级给人工。这种"不知道下一步会发生什么"的场景，才是 agentic AI 真正区别于传统规则系统的地方。

**（4）视觉计算机使用（Visual Computer Use）：**

让 agent 像人类一样看屏幕、使用浏览器——通过视觉理解界面 + 推理决策 + 工具调用 + 状态跟踪来完成操作。这个方向在课程录制时还比较前瞻。

**任务难度光谱：**

- **较易**：流程清晰固定、标准程序、纯文本输入输出
- **较难**：步骤未知、需要边执行边判断、多模态输入

> 客服 agent 的例子让人印象很深——这跟传统 chatbot 有本质区别。传统 chatbot 是"用户问 → 匹配意图 → 调预定义 API → 返回模板回答"，而 agentic 客服是"理解问题 → 自己判断需要哪些信息 → 动态决定调用顺序 → 根据中间结果调整——答不上来就升级给人"。发票处理的例子也体现了"LLM 做大脑、工具做手脚"的基础分工模式。

### 1.5 任务分解（Task Decomposition）

任务分解是构建 agentic workflow 的核心技能。课程给出了一套**四步方法论**：

1. **观察人类行为**：思考一个人会如何完成这个任务——每一步脑子里在想什么
2. **拆解步骤**：将任务拆成独立、清晰的子步骤
3. **评估可行性**：每个子步骤能否用 LLM 或工具实现
4. **迭代优化**：效果不好就进一步细化

**写论文的分解对比实验：**

| 方法 | 步骤数 | 流程 | 效果 |
|------|:---:|------|------|
| 方法一 | 1 步 | 直接生成 | 内容表面化，缺乏深度 |
| 方法二 | 3 步 | 大纲 → 搜索 → 撰写 | 内容更丰富但可能前后脱节 |
| 方法三 | 5 步 | 大纲 → 搜索 → 初稿 → 反思修订 → 定稿 | 质量显著提高 |

**基本构件（Building Blocks）：**

- **模型**：LLM（文本生成、决策）、其他 AI 模型（PDF 转文本、语音识别、图像理解）
- **工具**：API 调用、信息检索（Web Search, RAG）、代码执行

> 这里面有一个很重要的经验——**当你发现某一步 LLM 搞不定的时候，不要急着换模型或加数据，先问问自己"如果是人来做这一步，脑子里在想什么"，然后把那个思考过程拆成机器能执行的子步骤。** 这听起来简单，但实际操作中很容易被忽略——开发者经常对着一个不够好的输出反复调 prompt，其实真正需要的是把这一步拆成两步。

### 1.6 评估（Evals）

课程在 Module 1 就花了一整节讲评估——吴恩达的核心理由是：评估是驱动迭代优化的核心。没有评估就不知道改了之后到底有没有变好，只能靠感觉，而感觉经常是错的。

**核心方法论四步走：**

1. **先构建，再观察，后评估** —— 在构建 agentic workflow 之前，很难预见到所有可能出错的地方。所以不要一开始就试图设计完备的评估标准，而是先做一个初步版本，手工检查输出，找到希望改进的地方。
2. **识别低质量输出** —— 例如客服 agent 处理投诉邮件时，回复中提到了竞争对手的名字（"我们比 CompCo 好多了"），这在商业场景中通常是不允许的。这类问题事先很难预料，需要跑起来之后才能发现。
3. **构建评估指标追踪错误** —— 把发现的错误量化。例如"提到竞争对手"这个错误，先列出所有竞品名称（CompCo, RivalCo...），然后写代码自动扫描所有 agent 输出，统计竞品被提及的次数：`if competitor in response: num_competitor_mentions += 1`。这样就建立了一个可精确测量的客观指标。
4. **使用 LLM 作为裁判** —— 当评估标准更主观时（比如文章质量），引入第二个 LLM 做评估。设计评分 prompt："请为以下文章分配一个 1 到 5 之间的质量分数，其中 5 是最好的：{文章}"。

**两种评估类型：**

| 类型 | 衡量对象 | 适用场景 | 示例 |
|------|----------|----------|------|
| **端到端评估** | 整个 agent 最终输出的整体质量 | 快速判断整体效果 | 一篇完整论文的最终评分 |
| **组件级评估** | 单个步骤或组件的输出质量 | 定位具体哪个环节出问题 | 第一步"提取关键信息"的准确率、第二步"查询记录"的召回率 |

两种评估配合使用，形成一个"发现问题 → 定位问题 → 修复 → 验证"的正向循环。

> 吴恩达在 Module 1 就讲评估，这在技术课程里不太常见——大多数课程都是讲完整个系统设计之后才简单提一下。但他的逻辑是对的：没有评估的迭代是盲目的。端到端评估回答"系统好不好"，组件级评估回答"哪里不好"——两个问题都很重要但答案不同。

### 1.7 四大设计模式

Module 1 最后把 agentic AI 的实践总结为四种设计模式，这也是后续模块的组织骨架：

| 模式 | 核心概念 | 要解决的问题 |
|------|----------|-------------|
| **反思（Reflection）** | 让模型对自己的输出进行检查、评估和改进 | "写完再看一遍" |
| **工具使用（Tool Use）** | 赋予 LLM 调用外部工具的能力，模型自主决策 | "不会的自己查、自己算" |
| **规划（Planning）** | 让模型自主决定完成任务所需的步骤序列 | "先想清楚怎么做再动手" |
| **多智能体（Multi-agent）** | 多个具有不同专长的角色协同工作 | "一个人干不完，组个团队" |

**多智能体性能数据（vs 单智能体）：**

| 任务 | 单智能体 | 多智能体 | 提升 |
|------|:---:|:---:|:---:|
| 人物传记撰写 | 66.0% | 73.8% | +7.8% |
| 多模态理解 (MMLU) | 63.9% | 71.1% | +7.2% |
| 国际象棋走子 | 29.3% | 45.2% | +15.9% |

> 这四种模式并非互斥——在实际系统中经常组合使用。例如一个编码 agent 可能同时使用反思（检查生成的代码）、工具使用（调用编译器）和多智能体（一个写代码、一个写测试）。

## 二、Module 2：反思设计模式

### 2.1 反思的三个层次

课程将反思模式定义为一种"出奇地简单"但效果显著的方法。核心思路不复杂：让模型生成一个输出，然后让它（或另一个模型）回头检查这个输出，发现问题就改进，然后再检查，直到满意为止。

**人类反思的类比：**

课程用写邮件为例演示了人类反思的过程——写完初稿后回头读，发现三个问题：日期模糊（"下个月"不够具体）、拼写错误（"fre"应为"free"）、格式缺失（没有签名），然后逐一修改得到改进版。AI 反思就是把这个过程工程化。

**反思的三个层次：**

**（1）基础版 — 硬编码的"提示-反思"工作流：**

- 第一阶段：向 LLM 发送初始 prompt（"写一封邮件..."），得到初稿 V1
- 第二阶段：将初稿 V1 作为新输入再次发给 LLM（可以是同一个模型，也可以换模型），但这次 prompt 变了——"请反思这封邮件草稿，写一个改进版本"
- LLM 分析自己的初稿，生成更高质量的终稿 V2

课程强调这个流程是"硬编码"的——工程师预先设计好整个过程，并非让模型自主决定何时反思。这是一种"可靠且易于实现的工程化方法"。

**（2）进阶版 — 不同模型分工协作：**

利用不同 LLM 的不同专长：用擅长快速生成的模型写初稿，用擅长逻辑推理和错误检测的"思考模型（Reasoning Model）"来做反思和改进。这相当于把"干活"和"检查"分给不同的人，发挥各自优势，实现 1+1>2。

课程给的比喻："有点像让一个初级工程师先写方案，然后让资深工程师 review。"

**（3）终极版 — 反思结合外部反馈：**

最强大的反思形式是引入外部反馈。单纯让模型"自查"是有上限的——模型只能在自己的知识范围内检查。但把代码执行的实际输出和报错信息（如 `SyntaxError: unterminated string literal`）喂给模型，让它基于这些客观、具体的信息来修改，效果会有质的飞跃。

以写代码为例的完整流程：
1. LLM 生成代码 V1
2. 在安全沙箱中执行代码 V1
3. 系统捕获实际输出和错误信息
4. 将代码 V1 + 输出 + 报错一起喂给 LLM 进行反思
5. LLM 基于真实执行结果修复错误，生成功能正确的代码 V2

**课程的总结定调：**

- 反思不是魔法，而是工程实践——不能保证 100% 正确，但能带来"适度的性能提升"
- 外部反馈是反思效果的关键——"如果你能运行代码、查询数据库或调用 API，把这些结果作为反馈输入，就能实现更深入的反思和更好的输出"
- 有机会获取额外信息时，一定要把它纳入反思流程——这是"提升系统鲁棒性和输出质量的核心策略"

> 课程把"反思"分成了三个层次，这个分层我觉得很有用。基础版只是"自查"，进阶版是"分工审查"，终极版引入了"外部客观信息"。三层之间的跨越不是量变而是质变——特别是引入外部反馈之后，模型不再只是在"自己的知识"里打转，而是可以接触训练数据之外的真实信息。像一个 RAG 系统，只做检索 → 生成，不加反馈环节，用户就会发现答案里的数据跟原文对不上。加一步——把答案和原文一起喂给模型，让它逐条核验事实——虽然多了一次 LLM 调用，但幻觉问题能显著减少。这其实就是反思模式最简单的应用。

---

### 2.2 为什么不能"一次到位"

课程引用了论文《Self-refine》的实证数据来回答这个常见质疑：如果能把 prompt 写得更详细，一次输出高质量结果，为什么还要折腾反思流程？

**实验设计：** 在 **7 种任务**、**4 个模型**（GPT-3.5、ChatGPT、GPT-4、Claude）上，对比"直接生成"和"加入反思步骤后"的表现。

**实验结果：** 加入反思步骤后，**每一个模型在每一种任务上都有提升**。即使是最强的 GPT-4，加了反思之后还能更进一步。

**课程解读：** 不管模型多强，"一次性生成"本身就有天花板。反思不是在弥补"模型不够好"的问题，而是在弥补"信息不完整"和"思维不充分"的问题——即使是最聪明的模型，也不可能在第一次尝试时就考虑到所有边界情况。

**提示词写作建议：**

- 明确指示反思动作：用"请审查"、"请检查"、"请验证"，不要用模糊的"让它更好"
- 指定具体的检查标准：不是"检查有没有问题"，而是"检查 HTML 代码是否语法正确"、"检查步骤之间是否有遗漏"

> Self-refine 的数据最有力的一点是——连 GPT-4 这种当时最强的模型，加了反思之后还能进一步提升。这说明反思不是一个"补救弱模型"的手段，而是一个通用的增强策略。关于提示词的建议也很实在，经常看到有人写"please make it better"，这种模糊指令模型根本不知道该看什么——你得告诉它具体检查什么维度。

---

### 2.3 图表生成工作流案例

课程用咖啡销售数据可视化的例子，完整演示了反思模式 + 多模态模型的组合应用：

**步骤一：直接生成。**

用户给一个包含多款饮品 2024 Q1 vs 2025 Q1 销售数据的 CSV 文件，让模型画对比图。模型首先生成 Python 代码，跑出第一版图表（V1）。

**步骤二：多模态反思。**

第一步的输出（V1 代码 + V1 图表图片 + 对话历史）打包作为新输入，喂给一个**多模态 LLM**。Prompt 引导它扮演"专家数据分析师"，从可读性、清晰度和完整性三个维度批判性评估图表。多模态模型能"看到"视觉问题——标签有歧义、颜色难区分、缺少数据标注——然后提出具体改进建议。

**步骤三：基于反馈改进。**

模型根据反思反馈生成修改后的代码 V2，执行得到改进版图表。课程指出其中最关键的设计是**角色分工**：初稿生成用一般的强模型即可，反思环节最好用推理能力更强的多模态模型——写初稿可以快，审稿需要更仔细。

**课程坦诚之处：**

反思并非万能。有些任务加上反思后提升很大，有些只是略有改善——具体效果需要在你的应用场景里实测。这一坦诚态度贯穿了整门课。

> 这个案例是 Module 2 最接地气的部分，因为它展示了反思不是"让同一个模型再想想"那么简单——而是引入了多模态能力来做视觉评审，本质上是一种"外部反馈"。一个细节：初稿用 GPT-4 生成，反思用更强的 reasoning model——这种"不同模型做不同事"的工程思路很重要，比在任何环节都用最强模型更经济。

---

### 2.4 外部反馈：性能天花板的三级跳

吴恩达用了一条"性能天花板"的渐进曲线来说明外部反馈为什么是最关键的催化剂：

1. **没有反思的纯 prompt 优化**：初期快速提升，但很快撞到天花板。因为 prompt 能解决的问题是有限的——无论你怎么调，模型都只在自己的训练知识里打转。

2. **加入内部反思**：曲线再次上扬。模型开始自我检查、自我修正，但又会碰到新天花板——模型内部知识的局限，它"不知道自己不知道什么"。

3. **加入外部反馈**：曲线继续上升。模型获得了超出训练数据的信息——代码执行结果、数据库查询返回值、正则扫描结果、网络搜索的最新数据——这些"新鲜信息"让模型有机会接触"它不知道的东西"。

**外部反馈的来源：**

| 反馈类型 | 示例 | 实现方式 |
|----------|------|----------|
| 代码执行结果 | 代码跑出 SyntaxError | 沙箱中执行，捕获 stderr |
| 数据库查询 | 查到的数据与预期不符 | 对比查询结果和 ground truth |
| 模式匹配 | 回复中出现了竞品名称 | 正则表达式扫描输出文本 |
| 事实核查 | "泰姬陵建于1648年" | Web Search 结果对比 |
| 数值校验 | 文章超过字数限制 | 字数统计工具 |

> 这三级跳的框架把"反思"从哲学概念变成了工程实践。最容易被忽略的是第三级——很多系统做完"自查"就停了，但实际上"外部反馈"才是真正拉开差距的地方。前面提到的 RAG 幻觉问题，本质就是只做了内部生成，没有给模型机会去对照外部事实来修正。

## 三、Module 3：工具使用

### 3.1 工具的本质与决策机制

吴恩达给出一个很直接的定义：**工具就是函数**。工具使用的核心是——模型不再是被动生成文本，而是主动判断"我现在需要调用哪个函数、传什么参数、拿到结果之后怎么办"。

**工具使用的完整闭环：**

```
输入提示 → 模型决策 → 工具执行 → 结果反馈 → 最终输出
```

**条件性调用（Conditional Calling）：**

模型需要区分哪些情况该调用工具、哪些不该调：
- 问"现在几点？"→ 需要实时数据 → 调用 `get_current_time()`
- 问"绿茶含多少咖啡因？"→ 内部知识可回答 → 不调用工具

这看似简单，但模型能做出这种区分本身就很关键——不该调的时候乱调浪费时间和成本，该调的时候不调答案是错的。

**多工具协作：**

对于复杂请求，模型可以串联调用多个工具形成工作流。课程以日历助理为例：`check_calendar()` → 找到空闲时段 → `make_appointment()`。模型决定先调哪个、后调哪个、怎么把前一步结果传给下一步。

> 工具使用最核心的认知转变是让模型从"回答者"变成"决策者"。它不再只是从训练数据里检索答案，而是判断当前信息够不够、需不需要去外面查一下、查完之后怎么整合结果。这个决策逻辑比工具本身更重要。

---

### 3.2 手动实现工具调用的完整流程

课程花了不少篇幅讲早期"手动提示工程"时代是怎么实现工具调用的。虽然现在可以直接用 OpenAI function calling 或 Anthropic tool use 的原生 API，但理解底层机制对于 debug 和进阶开发很有帮助——很多高级框架做的事情，本质上就是把下面这四个步骤自动化了。

**完整四步流程：**

**第一步：写好工具函数本身。**

比如 `get_current_time(timezone)`，一个普通的 Python 函数，通过系统 API 获取指定时区的当前时间。

**第二步：通过系统提示告诉模型怎么"请求"工具。**

这是关键。在系统 prompt 中写明：你有这样一个工具可用；如果你需要用它，请在你的输出中按以下格式返回：`FUNCTION: get_current_time("时区")`。模型本身不能真的调函数——它只是在生成文本，但通过 prompt 让它生成一种"约定好的格式"，相当于建立了一套"通信协议"。

**第三步：开发者的代码做"中间人"。**

拿到模型的文本输出后，用正则或字符串匹配检测有没有 `FUNCTION:` 关键字。有的话就提取函数名和参数，然后由开发者代码去真正执行这个函数。这个环节里开发者相当于翻译官——把模型的"意图"翻译成实际的函数调用。

**第四步：把执行结果喂回给模型。**

函数执行完后，把返回值拼接到对话历史中，再让模型基于真实数据生成最终的自然语言回答。例如问新西兰时间 → 模型输出 `FUNCTION: get_current_time("Pacific/Auckland")` → 开发者代码执行函数得到"凌晨 4:00" → 回传 → 模型包装成"现在是新西兰时间凌晨 4 点"。

**工具带参数的情况：**

如果工具需要参数（如 `get_current_time(timezone)`），流程完全一样——系统 prompt 中约定参数格式 `FUNCTION: get_current_time("时区值")`，开发者代码解析出函数名和参数值，执行后回传。

> 这整个流程看起来挺原始的——用字符串匹配来解析模型输出——但底层逻辑跟现在最先进的 function calling API 是一模一样的：描述工具 → 模型决策 → 外部执行 → 结果反馈。理解了这个"原始版本"，再看 OpenAI 的原生 tool use，无非是把第二步（系统提示）和第三步（解析）标准化了而已。

---

### 3.3 代码执行：更灵活的替代方案

与其给模型预定义一堆工具函数，不如直接让它写代码，然后在安全环境里执行。这是 Module 3 中一个重要的设计选择。

**传统预定义工具方案的问题：**

用户问"13.2 加 18.9 等于多少"——给模型一个 `add(a, b)` 工具。但实际计算需求无限多：这次加法，下次"根号 2"，再下次要解微分方程。不可能为每种计算都预定义工具函数——现代科学计算器的功能太多了。

**代码执行方案：**

告诉模型"你可以写 Python 代码来解决问题，把代码放在 `<execute_python>` 标签里"。模型自主生成：

```xml
<execute_python>
import math
print(math.sqrt(2))
</execute_python>
```

系统用正则提取标签内的代码，在沙箱中执行，捕获结果 `1.4142135623730951`，传回给模型做最终回复。

**优势：**

相当于把整个 Python 生态都变成了模型的"工具集"。任何能用代码解决的问题，模型都能解决——不需要提前定义，极大地扩展了模型的能力边界。

**安全风险与对策：**

课程讲了一个真实事故：有人写的 agentic 代码执行器不小心执行了 `rm *.py`，把项目目录里的 Python 文件全删了（还好有备份）。所以**沙箱是硬性要求**——无论是 Docker 容器还是 E2B 这类专门为 AI agent 设计的隔离环境。

**与反思模式的组合：**

代码执行 → 拿到报错信息（SyntaxError + 行号）→ 作为外部反馈喂给模型 → 模型自己改 → 再执行。形成一个自动的 debug 循环。这恰好是 §2.1 中"终极版反思"的具体实现。

> 这一节对比"预定义工具"和"代码执行"两种方案，后者在灵活性和扩展性上的优势是压倒性的。当然，那个 `rm *.py` 的事故也足够让人警醒——写 agent 系统的时候，"能做什么"和"被允许做什么"是两个完全不同的问题，沙箱是必须的，不是可选的。

---

### 3.4 MCP（Model Context Protocol）

MCP 是 Anthropic 提出的开放标准，用于统一 LLM 与外部工具和数据源的连接方式。

**传统模式 vs MCP 模式的复杂度对比：**

| 传统模式 | MCP 模式 |
|----------|----------|
| m 个应用 × n 个工具 = **m×n** 个接口适配 | m 个应用 + n 个 MCP 服务器 = **m+n** |
| 每个应用独立编写工具封装 | 所有应用共享同一套 MCP 服务器接口 |

**核心组件：**

- **客户端（Clients）**：Claude Desktop、Cursor、Windsurf 等应用
- **服务器（Servers）**：Slack、Google Drive、GitHub、文件系统等数据和工具提供方

**能力演进：**

MCP 最初的设计偏重"获取数据"（fetch data），现在逐步扩展到支持执行操作（take action）。课程认为如果这个方向发展成熟，能显著降低 agent 开发的集成成本——不用每个新工具都写一套适配代码了。

> MCP 解决的核心痛点是"工具碎片化"——没有标准协议之前，每对接一个新工具都是一次重复劳动。这跟 API 标准化的逻辑是一样的：HTTP/JSON 出现之前，每个系统之间通信都要写自己的协议。MCP 本质上就是 agent 世界的 HTTP。

## 四、Module 4：构建 Agentic AI 的实用技巧

### 4.1 评估体系详解

Module 4 是课程最"工程化"的模块，围绕"怎么让 agent 系统从能跑变成跑得好"展开。第一件事还是评估——但这里的讲法比 Module 1 深入得多。

**开发原则：先快速原型，再评估迭代。**

不要一开始就试图设计完备的评估标准——在系统跑起来之前，很多问题是预测不到的。先做一个能端到端跑通的原型（哪怕很烂），手工看几个输出，找到表现不佳的地方，再针对性地构建评估指标。

**三个评估案例：**

**案例一：发票处理——日期提取（客观 + 有 ground truth）**

- 问题：系统经常混淆开票日期和到期日
- 测试集：10-20 张发票，手动标注正确的到期日
- 标准化：让 LLM 总是以 YYYY-MM-DD 格式输出日期
- 评估方法：正则提取日期，代码自动与 ground truth 比对

**案例二：营销文案——字数限制（客观 + 无 ground truth）**

- 问题：Instagram 配文经常超过 10 词限制
- 评估方法：代码计算输出文本的词数，对比 10 词上限
- 特点：没有每个例子的不同正确答案——目标（≤10 词）对所有例子都一样

**案例三：研究 agent——遗漏关键观点（主观 + 有 ground truth）**

- 问题：生成的论文有时遗漏专家认为重要的观点
- 测试集：每个话题准备 3-5 个"黄金标准点"
- 评估方法：使用 LLM 作为裁判，让评判 LLM 统计文章中覆盖了多少个黄金标准点

**评估设计的 2×2 矩阵：**

| | 客观评估（代码检查） | 主观评估（LLM 裁判） |
|---|---|---|
| **有 ground truth** | 发票日期提取（代码比对） | 黄金标准点统计（LLM 判断覆盖） |
| **无 ground truth** | 营销文案长度（代码计数） | 评分量表 Rubric（LLM 按维度打分） |

**LLM 作为裁判的注意事项：**

不要让模型直接比较两个回答（"哪个更好？"）——模型容易受**位置偏见**影响（倾向于选第一个或第二个）。正确的做法是分别打分，再对比分数。

**评估的迭代技巧：**

- 从 10-20 个样本的小型评估集开始，快速获取人工观察的辅助指标
- 随着系统和评估的成熟，逐步扩大评估集
- 如果系统改进了但评估分数没变 → 说明评估本身该升级了
- 以专业人士的行为为参考——找到系统与人类专家的差距，指导下一阶段的工作方向

> Module 4 是我觉得最"工程化"的一个模块。2×2 矩阵把评估设计简化成了一个清晰的决策框架——先问"有没有 ground truth"，再问"能不能用代码判断"，四个象限各有一种评估策略。从 10-20 个样本开始这个建议也很实用——构建评估集的常见误区是想一下子覆盖所有可能的问题类型，结果还没建完就放弃了。先针对最常出错的那几类问题构建，范围小但能立刻用起来。

---

### 4.2 错误分析与优先级

有了评估之后，下一步是搞清楚系统到底哪里不行。课程给出的做法很朴实但系统：

**核心方法：观察和量化，找出表现最差的组件。**

**关键概念区分：**

- **Trace（追踪）**：agent 运行过程中每一步产生的中间输出的整体——从输入到最终输出的完整轨迹
- **Span**：单个步骤的输出——trace 中的最小可分析单元

**错误分析三步走：**

1. **检查 Traces 和中间输出。** 不能只看最终结果。一个科研资料查询 agent 有三个步骤——搜索词生成 → 网页搜索 → 信息筛选——要分别检查每一步的中间产物：搜出来的词有没有歧义？返回的网页是不是学术来源？筛选的文章质量够不够？

2. **聚焦错误案例并量化。** 建立电子表格，统计每个组件出现错误的频率。哪个组件错误率最高，就先投入精力改进哪个。这不是感觉驱动，是数据驱动。

3. **不要凭直觉乱改。** 很多开发者看到输出不好就急着调 prompt、加功能，但没有量化的错误分析，他们不知道自己在修什么。系统越复杂，这种方式效率越差。

> 这个流程的本质就是"花钱在刀刃上"——先量化问题分布，再按优先级投入精力。Trace 和 Span 的区分也值得注意——如果你只看最终输出（相当于只看端到端评估），永远不知道是哪个环节拖了后腿。把每个 Span 的错误率统计出来，修哪里一目了然。

---

### 4.3 改进策略：从易到难的方法谱系

找到问题之后怎么改，课程给了一套有优先级顺序的方法谱系：

**非 LLM 组件改进：**

- 调整参数/超参数：搜索结果数量、RAG 相似度阈值、检测阈值
- 替换组件：换个搜索引擎、换个 RAG 方案、换个 Web Search API

这些改动通常很快就能验证效果，因为不涉及模型行为的变化。

**LLM 组件改进（按优先级排序）：**

| 优先级 | 方法 | 说明 | 成本 |
|:---:|------|------|:---:|
| 1 | **改进提示词** | 增加明确指令、使用少样本提示 | 低 |
| 2 | **尝试不同 LLM** | 多试几个模型，用评估数据选择最佳 | 中 |
| 3 | **任务分解** | 把当前步骤拆成更小、更易管理的子步骤 | 中 |
| 4 | **微调模型** | 最后手段——成本高、维护复杂、需要大量标注数据 | 高 |

**培养"模型选择直觉"的方法：**

吴恩达建议开发者多玩几个不同模型（至少 3-5 种主流模型），用自己积累的评估数据来判断什么模型适合什么场景。具体做法：
1. 频繁试玩不同模型
2. 建立个人的小型评估集
3. 阅读他人的提示词设计
4. 在工作流中实际轮换尝试

这比单纯看 benchmark 排行榜有用——通用 benchmark 跟你自己业务的特点往往对不上。

> 这里一个容易被忽略的关键点是——微调是最后手段，不是默认选项。很多时候 prompt 优化 + 换模型就能解决 80% 的问题，微调只有在前面方法都穷尽了才值得考虑。关于"选模型直觉"的建议也值得重视——benchmark 排名高的模型在你的具体任务上不一定表现最好，用评估数据说话比什么都靠谱。

---

### 4.4 延迟与成本优化

课程在这部分定了一个重要基调：**对于早期项目，高质量输出比延迟和价格重要得多。** 系统先跑出好结果，用户认可了，再来优化速度和成本——不要过早优化。

**延迟优化：**

核心手段是**计时基准测试**——把 workflow 里每个步骤的耗时记录下来（比如某一步 LLM 调用花了 7 秒，另一部分花了 18 秒），画出时间线就能一眼看到瓶颈。

两个最直接的优化方向：
- **并行化**：独立步骤并发执行（比如同时爬多个网页），总耗时取决于最慢的那个
- **更换模型**：把慢步骤换成更快的模型——即使能力稍弱一点，只要最终结果差距不大就是值得的；也可以试试不同提供商的同款模型，token 返回速度差异可能很大

**成本优化：**

- LLM 调用按 token 计费（输入和输出分开算）
- API 调用按次数计费
- 计算资源按服务器规格计费

识别出最贵的环节，优先考虑替换方案。有时候换一个性价比更高的模型提供商就能显著降成本。

> 延迟和成本优化是 Module 4 里容易被忽略但实际很重要的内容。"质量先过关再谈优化"这个排序很重要——有些团队一开始就纠结于"每次调用多花了 0.5 秒"，但系统输出的质量本身还没过关，这种优化是舍本逐末。

### 4.5 开发流程全景回顾

Module 4 最后把整个开发过程总结为四个迭代阶段：

| 阶段 | 描述 | 主要活动 |
|:---:|------|----------|
| **1. 快速原型** | 先做个能跑的东西 | 手工检查输出，凭直觉找问题 |
| **2. 初步评估** | 超越纯手动观察 | 构建端到端评估，小数据集（10-20 样本） |
| **3. 严谨分析** | 更精确的改进方向 | 错误分析，量化各组件错误频率 |
| **4. 高效调优** | 组件级改进 | 构建组件级评估，精准迭代 |

**吴恩达的关键观察：**

很多经验不足的团队花太多时间在**构建**上，太少时间在**分析**上。系统搭好之后就一直调 prompt、加功能，但从不回头看看哪个组件到底出了多少错、问题集中在什么地方。开发是非线性过程——需要在调整系统、错误分析、改进组件和调整评估之间反复横跳。系统化的开发流程（评估 → 错误分析 → 改进）才能支撑起足够复杂的 agent 系统。

> 这其实是很多小团队和独立开发者容易中的招——搭完之后就一直改代码，从来没有系统地统计过错误分布。这种"改一步看一步"的方式，在系统足够复杂之后效率会急剧下降。

## 五、Module 5：高度自治智能体的模式

### 5.1 规划设计模式

规划（Planning）设计模式的核心是：**不提前硬编码工具调用的顺序**，而是给模型一个工具清单、一个任务描述，让它自己决定先用哪个工具、后查什么、什么时候该停。

**客服 Agent 完整案例：**

课程构建了一个客服助理，给了 LLM 六个工具：

| 工具名 | 功能 | 示例 |
|--------|------|------|
| `get_item_descriptions` | 获取商品描述/元数据（名称、款式、颜色等） | 找到所有标记为"圆形"的太阳镜 |
| `get_item_price` | 查询商品价格 | 筛选 $100 以下的 |
| `check_inventory` | 检查库存状态和数量 | 确认有没有货 |
| `check_past_transactions` | 查询历史交易/退货记录 | "上周买的眼镜有问题" |
| `process_item_sale` | 处理购买（创建销售单） | 用户确认后执行购买 |
| `process_item_return` | 处理退货 | 用户要求退货时执行 |

**LLM 自主规划的流程：**

用户问"找一款 $100 以内的圆形太阳镜"：
1. 调用 `get_item_descriptions` 找"圆形太阳镜"
2. 拿到商品列表后，调用 `check_inventory` 查库存
3. 对库存中的商品，调用 `get_item_price` 筛选 $100 以下的
4. 整合结果输出给用户

这个流程不是人提前写好的——是模型根据当前任务自己"想"出来的。

**优缺点分析：**

| 优点 | 风险 |
|------|------|
| 能力丰富，任务覆盖范围远超硬编码 | 运行时无法预知 LLM 会生成什么计划 |
| 无需事先编排工具调用序列 | 结果不稳定、可能出错、可能越权 |
| 灵活性和自主性高 | 目前在 AI Coding 最成功，其他领域仍在探索 |

**课程额外经验：**

工具设计的粒度很关键。经验丰富的开发者可能只需三个封装良好的工具就能解决问题；经验不足的可能过度抽象出十几种工具，或者反过来只给一两个过于基础的工具——比如"直接给一个数据库 session 让 AI 自己写 SQL"——这非常危险。

> 规划设计模式的核心权衡是"可控性 vs 能力边界"。这个模式最有趣的地方在于——放弃了对执行步骤的精确控制，换来更广的任务覆盖范围。客服 agent 那个案例尤其直观：6 个工具给模型之后，它能处理的用户请求种类远超出任何预定义的对话流程树能覆盖的范围。

---

### 5.2 用代码代替 JSON 表达计划

在规划设计模式中，一个常见做法是让 LLM 用 JSON 描述计划——每一步做什么、用什么工具、参数是什么。但课程指出，越来越多的研究发现：**让 LLM 直接写 Python 代码来表达执行计划，效果比输出 JSON 更好。**

**HuggingFace smolagents 框架的 CodeAgent 就是基于这个思路设计的。**

**三个优势：**

1. **利用庞大代码库**：代码可以直接调用 Pandas、NumPy 等库的数千个内置函数，表达能力远超 JSON 的键值对
2. **高表达力**："解析日期、排序、过滤、去重再计数"这种多步骤逻辑，用代码几行就写清楚了，用 JSON 会非常冗长且容易出错
3. **更好的评估得分**：在多项研究和多轮评估中，代码方案的得分确实比 JSON 方案更高

**代价：**

直接执行模型生成的代码存在安全风险，沙箱是硬性要求。另外，需要在系统 prompt 中明确告诉 LLM 用 `<code>` 标签或反引号包裹代码。

**框架评价：**

课程推荐了 HuggingFace 社区的 smolagents 框架——代码简洁、抽象层少、工具开发只需一个 `@tool` 装饰器、内置工作流追踪。容易上手，也便于理解底层逻辑和自定义扩展。

> 这是一个让我觉得很新鲜的观点。用 JSON 描述计划其实很"不自然"——JSON 擅长数据交换，不擅长描述逻辑。"先用 Pandas 解析 CSV，然后按日期分组，再按销售额降序排列"这种事，用 Python 三行就写完了，用 JSON 得写一页。CodeAgent 的思路让 agent 从"填表格"变成了"写脚本"，表达能力上了一个量级。

### 5.3 多智能体工作流

多智能体的基本出发点很朴素：有些任务太复杂，一个 agent 搞不定，那就让多个 agent 各管一块。

**为什么需要多智能体：**

课程给出了四个理由：

1. **任务分解**：像人类团队一样，把复杂任务拆成多个子任务，每人负责一块
2. **专注性**：单个 agent 的任务越简单、范围越窄，效果越好——让一个 agent 同时做"调研 + 写代码 + 检查"不如三个 agent 各做一件
3. **模块化与复用**：通用的 agent（如"研究者"、"代码审查者"）可以跨应用复用
4. **创建方式简单**：不同 agent 的区别只是 prompt + 工具的组合不同，不需要写复杂的新系统

**两个容易被忽略的工程优势：**

**突破上下文限制。** 单个 LLM 的上下文窗口是有限的——即使支持 200K token，上下文越长推理越慢、成本越高，而且模型对长文本中间段的理解存在退化。多智能体的做法是：每个 agent 只看自己负责的那部分信息，最后的汇总 agent 只看各个 agent 的结论摘要。这样总信息量可以远超单个上下文窗口的容量。

**省钱省时间。** 上下文越短，输入 token 越少，API 费用越低，推理速度也越快。而且多个 agent 可以并行工作——同时启动三个 agent 分别调研不同方向，总耗时取决于最慢的那个，而不是所有加起来。

> 多智能体的两个工程优势——突破上下文限制 + 省钱省时间——其实比"分工协作"这个表面理由更有说服力。特别是上下文限制，不管你模型窗口多大，让一个 agent 在一个超长上下文里处理所有信息，效率和准确率都会下降。拆给多个 agent 各管一块，汇总者只看摘要，是更合理的信息架构。这跟软件开发里的微服务思路很像——不是因为单体架构做不了，而是拆开之后更可维护。

### 5.4 四种通信模式

课程把多智能体之间的通信模式分成了四种，各有适用场景：

**（1）线性模式（Linear）：**

顺序执行，单向通信。Agent A 产出 → Agent B 处理 → Agent C 继续。优点是简单可控，缺点是不够灵活。适合流程固定的任务，如"写大纲 → 查资料 → 写正文"。LangChain 框架偏重这种结构。

**（2）双层/层级模式（Hierarchical）：**

有一个 Manager Agent 居中协调，给下面的执行 agent 分配任务、汇总结果。控制力强，适合需要统一调度的多任务场景。但管理负担全在 manager 上，而且信息在层级传递中会丢失——层级越多，末端 agent 拿到的信息越稀薄。smolagents 框架倾向这种结构。

**（3）多层模式（Deep Hierarchy）：**

在双层基础上把执行层的 agent 再做层级化。更模块化，适合大型系统，但复杂度显著增加。

**（4）去中心模式（All-to-all）：**

所有 agent 自由对话、互相交流。创造性强，适合探索型任务。但行为不可预测，工程上难以控制。MetaGPT、CAMELAI 在探索这个方向。

**实践中的取舍：**

吴恩达指出，实际应用中最常见的是线性和双层模式——不是因为它们最强大，而是因为它们最可控。去中心模式虽然理论上能力更强，但在生产环境中很难管理。核心判断标准是：在"可预测性"和"灵活性"之间做取舍。

> 这四种模式的选择本质上是 trade-off——线性最可控但最不灵活，去中心最灵活但最不可控。大多数生产系统选线性和双层，不是保守，而是因为生产环境对"可预测性"的要求远高于学术实验。一个重要的工程经验是：信息在层级传递中会衰减，层级越多损耗越严重——这跟人类组织里的"信息漏斗"是一回事。

```

    ↓

    ↓
Module 3: 工具使用 → 实现机制、代码执行、MCP 标准化
    ↓

    ↓
Module 5: 高级模式 → 规划、代码执行规划、多智能体、通信模式
```

### 几个贯穿全文的脉络

**工程化与算法创新之间的关系。** HumanEval 上 GPT-3.5 + agentic workflow 能超过 GPT-4 zero-shot——在基础模型能力相同的前提下，工作流设计和工程实践带来的性能差距可能比模型升级还要大。课程反复强调的评估、错误分析、组件级追踪、渐进式优化，本质上都是软件工程的实践。

**自主性是渐进式的，不是一步到位的。** 课程始终坚持"agentic 是光谱而非标签"的定位——在开发早期，可控性和可调试性比智能化程度更重要。先把步骤固定下来跑通，再逐步把决策权交给模型。

**提示词 + 评估 + 外部反馈构成闭环。** 单独做 prompt engineering 迟早撞到天花板，但当它和外部反馈（代码执行结果、API 返回数据、网络搜索）结合在一起，天花板就被抬高了。再加上系统化的评估和错误分析，整个改进过程就有了方向——知道该修哪里、怎么验证修好了。

课程最后的一个观点可以作为整个方法论的精炼：**不要一开始就追求完美架构，先做个能跑的东西出来，然后让评估数据告诉你下一步该修什么。** 这不只适用于 agentic AI。
