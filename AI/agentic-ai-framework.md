## 1. 核心概念：Agent 到底是什么

### 1.1 社区共识公式

Hugging Face 的 Agent Glossary 给出了当前社区逐渐收敛的定义：

```
Agent = Model + Harness
```

**Model（模型）** 是 LLM 本身——接收文本、输出文本。Claude、GPT、Qwen、DeepSeek 都是 Model。它在单次调用中**没有记忆、没有循环**，可以表达"我想调某个工具"的意图，但本身不能执行。

**Harness（执行框架）** 是包裹在模型外面的运行层。它负责三件事：调用模型、处理模型返回的工具调用请求、决定什么时候停止。Harness 的质量决定了同一个模型在不同产品中的表现差异——两个产品使用同一个模型但体验截然不同，差别就在 Harness 上。

**Scaffolding（脚手架）** 是 Harness 内部的行为定义层：系统提示词、工具描述、响应解析规则、上下文管理策略。它塑造了模型"看世界和行动"的方式。

这三个概念的嵌套关系可以这样理解：

```
┌─────────────────────────┐
│         AGENT           │
│  ┌───────────────────┐  │
│  │     HARNESS       │  │
│  │  ┌─────────────┐  │  │
│  │  │  SCAFFOLD   │  │  │
│  │  │  ┌───────┐  │  │  │
│  │  │  │ MODEL │  │  │  │
│  │  │  └───────┘  │  │  │
│  │  └─────────────┘  │  │
│  └───────────────────┘  │
│       SUB-AGENT         │
└─────────────────────────┘
```

这个视角澄清了一件容易混淆的事：**Model、Harness、Product 是三个不同的东西**。产品是用户最终看到的应用（Claude Code、Cursor、Codex CLI），它在 Harness 之上叠加了 UI、文件系统集成、沙箱管理、用户偏好等更多层。

### 1.2 Agentic AI 的本质

从 agentic.ai 的定义来看：**Agentic AI = 能够行动的 AI**。它不是一个新"物种"，而是在 LLM 之上叠加了"决定 → 行动 → 观察"循环的系统。

关键认知：
- **Agenticness 是一个光谱，不是二元标签**。不存在"是 agent"和"不是 agent"的二分法，每个系统在不同维度上有不同程度的自主性。
- 分界线在于系统是否在**循环中采取行动**——聊天机器人回答完就停，Agent 会观察结果、决定下一步、直到任务完成。
- 术语 "agentic" 源自 *agency*（能动性）——对世界施加影响的能力。

### 1.3 "Agent" 词义的演变

社区观察到一个有趣现象：**"Agent" 这个词每年的含义都在变**。去年还聚焦在"自主性"上，今年的讨论重心已经转移到"Model + Harness"的工程组合上。有社区成员提出了更精确的命名方案——Coding Agent（命令行应用）、Agent Definition（Markdown/JSON 蓝图）、Agent Instance（运行中进程）——建议避免单独使用含义模糊的 "Agent"。

## 2. 架构分层：Agent 的内部结构

### 2.1 三层模型

| 层 | 职责 | 类比 |
|---|---|---|
| **Model** | 文本→文本推理，表达意图 | 大脑 |
| **Scaffolding** | 系统提示、工具描述、响应解析、上下文策略 | 认知框架 |
| **Harness** | 调用模型、路由工具调用、终止控制 | 执行系统 |

### 2.2 关键区别：Tool vs Skill vs Sub-agent

这三个概念在实践中经常被混用，HF Glossary 做了明确区分：

| 概念 | 本质 | 示例 |
|------|------|------|
| **Tool（工具）** | 单个动作 | "执行这条命令" |
| **Skill（技能）** | 完成一个目标所需的完整知识包 | "调查这个 bug，形成假设，写出修复" |
| **Sub-agent（子代理）** | 被另一个 agent 调用的独立 agent，有自己的 model 和 scaffold | 主 agent 派一个子 agent 去调研某个模块的代码 |

Skill 可以跨 agent 复用、按需加载。Sub-agent 与 Tool 的本质区别在于：sub-agent 可以自己推理、自己使用工具、甚至自己再调用子 agent。

### 2.3 Agentic 循环（ReAct 循环）

无论多复杂的 agent 系统，底层都运行同一个基本循环：

```
┌─────────────────────────────────────┐
│   Decide ──→ Act ──→ Observe        │
│     ↑                   │           │
│     └───────────────────┘           │
└─────────────────────────────────────┘
```

| 阶段 | 内容 |
|------|------|
| **Decide** | 审视目标与当前状态，选择下一步：搜索、写代码、调 API、问用户、或停止 |
| **Act** | 通过 Harness 执行：HTTP 请求、文件编辑、Shell 命令、浏览器操作、函数调用 |
| **Observe** | 读取结果、更新记忆、检测错误；判断继续/重试/换策略/结束 |

这一模式在 2022 年的 ReAct 论文中被形式化。现代 agent 在此基础上增加了 Planning（规划）、Memory（记忆）和 Multi-agent coordination（多智能体协调）。

## 3. 工程框架：ETCLOVG 七层分类法

CMU、Yale 等机构在 2026 年发表的综述《Agent Harness Engineering: A Survey》提出了 **ETCLOVG** 分类法，将 agent 的基础设施抽象为七个独立层。这七个层分为两组：前四层是**结构支柱**，后三层是**控制平面**。

### 3.1 结构支柱（Structural Pillars）

#### E — Execution Environment（执行环境）
agent 的代码在哪里运行、受到怎样的沙箱约束。

| 子类别 | 说明 |
|--------|------|
| 托管沙箱 | Docker、E2B 等容器化隔离 |
| 微型虚拟机 | Firecracker 等轻量 VM |
| 代码专用运行时 | Python exec()、Jupyter kernel |
| 计算机使用环境 | 完整桌面或浏览器沙箱 |
| OS 级权限模型 | 文件系统访问控制、网络限制 |

#### T — Tool Interface and Protocol（工具接口与协议）
外部能力如何被描述、发现和调用。

| 子类别 | 说明 |
|--------|------|
| 协议标准 | MCP、A2A 等开放协议 |
| 工具描述与选择 | 如何为模型提供工具菜单并让它选择 |
| 工具增强训练 | 通过训练让模型学会更准确地使用工具 |
| 会话管理 | 跨多轮调用的工具状态维护 |

#### C — Context and Memory Management（上下文与记忆管理）
模型在每个时间步能看到什么——跨短期、会话级和持久化三个时间尺度。

| 子类别 | 说明 |
|--------|------|
| 长上下文技术 | 检索增强、压缩、注意力优化 |
| 上下文漂移缓解 | 防止模型在执行长任务时偏离原始目标 |

**记忆的两个层次：**
- **短期记忆**：在一次运行期间保留在上下文窗口内（对话历史、工具结果、推理过程）
- **长期记忆**：跨会话持久化，外部存储、按需检索

#### L — Lifecycle and Orchestration（生命周期与编排）
读写状态的控制流。

| 子类别 | 说明 |
|--------|------|
| 单 agent 内部循环 | 一个 agent 的 Decide→Act→Observe 循环 |
| 多 agent 模式 | 多个 agent 的分工与通信 |
| 端到端任务管道 | 从 issue 到 PR 的完整自动化流程 |

### 3.2 控制平面（Control Plane）

#### O — Observability and Operations（可观测性与运维）
捕获追踪、成本、故障和可靠性信号。

| 子类别 | 说明 |
|--------|------|
| 追踪平台 | 记录 agent 每一步的决策和结果 |
| agent 专用运维工具 | 面向 agent 系统的监控 |
| 成本追踪 | Token 消耗、API 调用次数的实时统计 |
| 统一可观测性 | 将模型调用、工具执行、错误日志整合到同一视图 |

#### V — Verification and Evaluation（验证与评估）
将任务/追踪转化为评估结果、故障归因和回归反馈。

| 子类别 | 说明 |
|--------|------|
| 基准锚定 | SWE-bench、AgentBench、GAIA 等标准化测试 |
| 受控执行 | 在固定环境中重复运行以消除随机性 |
| 多级评判 | LLM-as-judge + 代码验证 + 人工评审的组合 |
| 部署时评估循环 | 生产环境中的在线评估与回归检测 |

#### G — Governance and Security（治理与安全）
在模型级、系统级、组织级三个层面对行为施加约束。

| 子类别 | 说明 |
|--------|------|
| 权限模型 | agent 可以做什么、不能做什么 |
| 生命周期钩子 | 在关键节点插入审批或审计 |
| 组件加固 | 防止 prompt 注入、目标错位等攻击 |
| 声明式章程 | 用自然语言定义的 agent 行为准则 |
| 审计基础设施 | 完整的操作记录与回溯能力 |

### 3.3 开源项目分布

综述对开源生态做了系统映射（当前快照）：

| 层 | 范围 | 主要项目数 |
|---|------|:---:|
| E | 执行环境与沙箱 | 20 |
| T | 工具接口与协议 | 12 |
| C | 上下文与记忆管理 | 9 |
| L | 生命周期与编排 | 47 |
| O | 可观测性与运维 | 15 |
| V | 验证与评估 | 21 |
| G | 治理与安全 | 14 |

**观察到的模式：**
- **E、T、L、V 层最密集**——编码、Web、终端和计算机使用 agent 都需要可运行环境、工具契约、控制循环和可重复评估。
- **C 层（上下文与记忆）** 常以嵌入式组件形式出现在更大的框架中，独立项目较少。
- **O 和 G 层** 在开源生态中覆盖最薄——它们更多存在于商业平台、SDK 特性或工程文档中，标准化程度落后于运行时和基准测试基础设施。

## 4. 工程演进：Prompt → Context → Harness Engineering

综述提出了 agent 工程重心的三阶段迁移，每个阶段对应一个核心问题：

| 阶段 | 时间 | 核心问题 |
|------|------|----------|
| **Prompt Engineering** | 2022–2024 | "输入什么提示词？"——指令、少样本示例、推理模板，面向单次模型调用优化 |
| **Context Engineering** | 2025 | "模型在每个步骤应该看到什么？"——扩展到检索、压缩、工具结果排序、上下文窗口管理 |
| **Harness Engineering** | 2026– | "整个基础设施包装层怎么做？"——执行环境、工具接口、上下文、生命周期、可观测性、验证、治理 |

这个迁移过程在开源系统的演化中清晰可见：
- **2022–2023**（ReAct 时代）：用 while 循环 + prompt 模板 + 简单工具分发表包装单模型。AutoGPT 和 BabyAGI 暴露出的问题——执行失控、上下文爆炸、状态丢失、无监控副作用——本质上都是基础设施问题。
- **2023–2024**（工具集成与多 agent）：出现了学习式工具使用（Gorilla、ToolLLM）、角色扮演式组织（CAMEL、ChatDev、MetaGPT）、首批基准（SWE-bench、AgentBench）和协议标准化的萌芽（MCP、A2A）。
- **2025–2026**（Harness Engineering 成为独立学科）：社区开始用这个名称来命名这一领域，出现了只变化 Harness 而固定模型的对照实验，证明 Harness 本身就是一个独立的设计变量。

### 核心论点

综述提出了三个核心主张：

1. **Harness 是独立的系统层。** 可靠性不只来自模型能力，还来自执行控制、反馈循环、治理策略、评估方法和运维设计。

2. **ETCLOVG 分离了生产环境的关注点。** 七层架构揭示了早期框架中常被混在一起的架构边界——在生产部署中，每一层都有自己的工具栈，通常由不同团队负责。

3. **生态映射揭示空白。** 系统性地遍历开源生态后，可以清晰看到哪些层工具成熟、哪些层还是空白——O 和 G 层的开源选项明显不足。

## 5. 训练视角：RL 与 Agent 的交汇

Hugging Face Glossary 专门梳理了 RL 训练管线中的核心术语，这部分对于理解 agent 的"学习机制"很重要：

### 5.1 RL 训练管线

```
RL Environment ←→ Agent (运行 Rollout) → Reward → Trainer → 更新 Model 权重 → 回到 Agent
```

### 5.2 关键术语

| 术语 | 定义 |
|------|------|
| **RL Environment** | 有状态对象：接收 action，更新内部状态，返回 observation。在 LLM 场景中，action 通常是工具调用 |
| **Rollout（轨迹）** | 一次完整的 agent 运行记录：每一步看到了什么、做了什么、得到了什么奖励。这是 RL 算法学习的原始数据 |
| **Reward（奖励）** | 告诉训练算法模型是否在进步的分数。分为可验证型（测试通过/失败）和学习型（人类偏好、LLM-as-judge）；可稀疏（仅结尾给分）或密集（每步给分） |
| **Trainer** | 负责让 agent 变好的组件——运行大量 episode、对结果评分、用分数更新模型权重。例如 TRL 的 `GRPOTrainer` |
| **Policy（策略）** | agent 遵循的行为规则——给定任意状态，定义采取每种可能行动的概率。注意：Policy 不是 Agent——Policy 定义行为，Agent 是在环境中行动的完整系统 |

### 5.3 Rubric（评分量表）机制

Rubric 将奖励拆分为显式的维度，每个维度有权重。例如 OpenEnv 和 Verifiers 将评分维度实现为可组合对象：`WeightedSum`（加权求和）、`Sequential`（顺序评分）、`Gate`（门控条件）。

## 6. 评估维度：如何衡量 Agentic 程度

### 6.1 agentic.ai 的九维评分体系

agentic.ai 对每个工具在九个维度上评分 0–4 分（总分 0–36），这是一套面向产品选型的实用评估框架：

| 维度 | 评估问题 |
|------|----------|
| **Action Capability** | 能执行真实行动吗？ |
| **Autonomy** | 能自己选择下一步吗？（无需人工逐步审批） |
| **Planning & Reasoning** | 能分解多步目标吗？ |
| **Adaptation & Recovery** | 出错后能换条路走吗？ |
| **State & Continuity** | 能跨步骤、跨会话携带上下文吗？ |
| **Reliability** | 输出是否稳定、可复现？ |
| **Safety & Observability** | 有护栏（权限、审计日志）吗？ |
| **Interoperability** | 能和其他工具/协议（MCP 等）协作吗？ |
| **Operator Sovereignty** | 人类是否保持最终控制权？ |

### 6.2 六个 Agentic 等级

| 等级 | 分数 | 特征 | 典型示例 |
|------|:---:|------|----------|
| **L0 反应式工具** | 0–5 | 仅响应提示，不采取自主行动 | 基础聊天机器人 |
| **L1 引导式助手** | 6–11 | 在狭窄领域内逐步执行，需每步指令 | 按指令编辑单文件的 Copilot |
| **L2 自适应协作者** | 12–17 | 提出并执行多步计划，关键步骤需审批 | Claude Code、OpenHands |
| **L3 领域专家** | 18–23 | 独立完成领域内工作流，动态重规划 | GitHub Copilot、Cline、Windsurf |
| **L4 自主操作者** | 24–28 | 跨领域复杂工作流，自纠错 + 企业安全 | 无监督外呼营销 agent |
| **L5 战略代理** | 29–32 | 自行设定子目标，跨系统持续运作 | 长期运行的自导向 agent |

| 能力 | 聊天机器人 | Copilot | Agentic AI |
|------|:---:|:---:|:---:|
| 生成文本/代码 | ✅ | ✅ | ✅ |

| 跨会话持久记忆 | 有限 | 有限 | ✅ |

## 8. 系统约束：工程中的三个核心权衡

综述从七层交叉分析中提炼出三个反复出现的系统级约束：

### 8.1 成本–质量–速度三元悖论

更强的沙箱、更丰富的上下文、更深入的评估确实提升质量——但代价是更多的 token 消耗、更高的延迟和更重的基础设施开销。生产级 Harness 必须判断哪些风险值得用昂贵的安全控制来应对，哪些可以异步处理或放在回归测试套件中。

### 8.2 能力–控制权衡

更大的工具菜单、持久记忆、宽松的沙箱权限能扩展 agent 的能力范围，但也放大了出错的爆炸半径。能力和控制不是两个独立变量，而是**同一条设计轴的两端**，横跨工具 schema、上下文策略、运行时权限、身份认证、可审计性和人工审批。

### 8.3 Harness 耦合问题

七个层之间存在耦合——一个组件（prompt、工具、沙箱、验证器、监控器）在隔离状态下看起来是改进，但当它与控制循环的其余部分组合时，可能反而使整体表现退化。Harness 的改动应该作为**系统级变更**来测试，而非组件级。这引申出一个更宏观的趋势：从 **Agent Framework**（打包 agent、工具、记忆等本地抽象）到 **Agent Platform**（叠加持久工作空间、身份认证、可观测性、评估、治理和跨多次运行及多用户的人类交接）。

## 9. 五个开放问题

综述基于七层交叉分析提出了五个研究方向：

1. **执行环境的加固与扩展**——prompt 注入、目标错位、组合放大的通用安全评估；在不同隔离级别（容器 vs 微 VM vs 桌面 VM vs 浏览器沙箱）之间做成本建模；自托管/云端/混合部署之间保持语义可移植性。

2. **长运行 agent 的可靠状态管理**——将上下文管理重新定义为状态估计问题；量化每一步压缩、检索或遗忘中的信息损失；引入溯源、矛盾处理、显式过期标记；从持久化的制品而非压缩的历史中恢复状态。

3. **以追踪为中心的故障诊断**——追踪（trace）应该成为"系统从中计算输出分数、轨迹质量、故障归因和回归测试的主要对象"，而不仅仅是事后调试工具。当前可观测性工具的广泛采用与离线评估的相对滞后之间的差距，正是突破口。

4. **跨 agent、工具和人类的标准化交接**——交接不应只传递一段文本摘要，而应传递意图、约束、权限、制品、溯源、预算状态、风险等级、追踪历史、未解决的决策。难点在于：协议既要足够丰富以保证安全，又要足够简单以保证采纳。

5. **随模型进步的自适应简化**——"每一个包装层都编码了关于模型在哪些事上还不可靠的假设。"随着模型变强，有些干预仍然是关键承重结构，有些则变成多余开销。未来的 Harness 需要能自我消融、优化和简化，在质量、延迟、成本和风险的联合约束下运行。

## 10. 关键术语汇总

| 术语 | 定义 | 来源 |
|------|------|------|
| **Model** | LLM 本身，文本→文本，无记忆无循环 | HF Glossary |
| **Scaffolding** | 行为定义层：系统提示、工具描述、解析规则、上下文策略 | HF Glossary |
| **Harness** | 执行层：调用模型、路由工具调用、终止控制 | HF Glossary |
| **Agent** | Model + Harness，在循环中感知、决策、行动 | HF Glossary |
| **Agentic AI** | 能自主追求目标、调用工具、观察调整的 AI 系统 | agentic.ai |
| **ReAct Loop** | Decide → Act → Observe 循环 | agentic.ai |
| **Tool Use** | 模型通过结构化格式表达调用工具的意图 | HF Glossary |
| **Skill** | 完成目标所需的可复用知识包，跨 agent 加载 | HF Glossary |
| **Sub-agent** | 被另一个 agent 调用、有独立 model/scaffold 的 agent | HF Glossary |
| **Orchestrator** | 协调多个 agent 工作的高层控制器 | HF Glossary |
| **Policy** | agent 的行为规则：给定状态 → 每种行动的概率 | HF Glossary |
| **Rollout** | 一次完整 agent 运行的记录（也称 trajectory/trace） | HF Glossary |
| **Reward** | 训练中告诉算法是否进步的分数 | HF Glossary |
| **ETCLOVG** | Execution / Tooling / Context / Lifecycle / Observability / Verification / Governance | LLM-Harness |
| **MCP** | Model Context Protocol，连接 agent 与工具/数据的开放标准 | 通用 |
| **Memory** | 短期（单次运行内的上下文）+ 长期（跨会话持久化） | 通用 |
| **Human-in-the-loop** | 在关键步骤暂停以获取人类批准 | 通用 |
| **Guardrails** | 限制 agent 行为范围的约束条件 | 通用 |
